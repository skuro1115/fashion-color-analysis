# 要望を整えるモード

利用者は非エンジニア。やりたいことを一緒に言葉にして、実装できる粒度の要望書にするのが目的。
**このモードではコードも設定も変更しない。** 成果物は `docs/requests/` の要望書だけ。

## 手順

1. **前提を読む**：`docs/roadmap.md`（3つの道具と、道具どうしの約束）、`AGENTS.md`、関係しそうなら `config.yaml`。
2. **どの道具の話か確かめる**：① 分析ツール / ② データ収集ツール / ③ パワポ作成 skill / その他。
3. **質問して整理する**
   - 一度に聞くのは **3 つまで**。選択肢を付けて、答えやすくする（使えるなら AskUserQuestion を使う）
   - 聞く順番の目安：目的（何を知りたい・決めたいか）→ できあがりのイメージ → 入力 → できたと言える条件 → やらないこと
   - 専門用語は使わない。使うときは一言で説明する（例「ΔE = 色の違いの大きさ」）
   - 利用者が決めきれないことは、推奨案を1つ示して選んでもらう
4. **実現性を確かめる**（コードを読んでよい、変更はしない）
   - `config.yaml` の変更だけで済むなら、そう伝える（要望書は小さくてよい）
   - `docs/roadmap.md` の「道具どうしの約束」や既存 CSV の後方互換に影響するなら、はっきり書く
   - ② ③ のように未着手の道具なら、「まだ作っていない」ことと、最初に作る最小の形を提案する
5. **要望書を書く**：`docs/requests/TEMPLATE.md` をコピーして `docs/requests/YYYY-MM-DD-<英小文字の短い名前>.md` を作る。状態は `下書き`。
   「7. AI メモ」は AI が埋める。`docs/requests/README.md` の一覧に1行足す。
6. **読み合わせる**：要点を 5 行程度で伝え、直したい所がないか聞く。合意できたら状態を `合意済み` にする。
   新しい構想なら `docs/roadmap.md` の候補表にも1行足す。
7. **次の一歩を伝える**：「実装して」と言われたら通常の改修 (AGENTS.md のルール) に進む、と伝えて終える。
   このモードの中で勝手に実装を始めない。

## 注意

- ② データ収集ツールの相談では、サイトの利用規約・robots.txt・著作権の確認が必要なことを必ず要望書の「決まっていないこと」に入れる。
- 要望が大きすぎるときは、最初の一歩（1〜2 日で作れる最小の形）と、あとでやることに分ける。
